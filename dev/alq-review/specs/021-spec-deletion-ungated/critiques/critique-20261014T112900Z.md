# Critique: A PR labelled cleanup gets no alq-review gating

**Spec**: [../spec.md](../spec.md) | **Plan**: [../plan.md](../plan.md) | **Date**: 2026-10-14 | **Tasks**: not generated

No `.specify/templates/critique-template.md` exists; structure follows the critique command's outline.

## Executive Summary

The plan is sound in shape: one pure decider (`is_cleanup`), the existing grant code reused, the label check placed in
`pre_merge_gate` so log mode cannot become a second way out, holds kept (R10), ADR first (R9). Two things need fixing
before tasks: the label-add refusal would also block labelling **issues** `cleanup`, which is ordinary triage; and the
label name reuses a general-purpose triage label as a review switch. The commit-check exemption (FR-012) costs gh calls
on every commit in every repo but cannot fire in the motivating flow, because those commits happen before the PR and
its label exist. That one needs the user's input.

**Verdict: ⚠️ PROCEED WITH UPDATES**

## Product Lens

### 3a. Problem validation
- Real, observed defect (#113, two manual `!` commands). Scope after the clarifications is a user-granted switch, not a
  diff classifier. That is simpler and also covers #113's citation edits (R12). Good.
- The feature folder is named `spec-deletion-ungated` and the Input still describes a diff rule. Nothing breaks, but a
  reader meets the opposite design first. (P4)

### 3b. User value
- US1/US2/US3 each deliver value. The user still does one thing per retired spec (the grant prompt), down from two
  `!` commands. SC-001 states this honestly.
- FR-012 / SC-002 (commit checks skipped): in `/alq-post-merge` step 7 the agent commits the deletion and the citation
  edits, *then* opens the PR, *then* the user grants the label. Every commit of the motivating flow runs before
  any PR carries the label, so the exemption does not apply to them. SC-002's "zero claim-check or shim-check runs
  on its commits" cannot be met for those commits. (X1)

### 3c. Alternatives
- Reusing the version-only-release mechanism (org gate classifies the diff) was rejected by Clarification 1. That is
  correct for `claude-plugins-internal`, where no org gate runs.
- Alternative for the grant: let the `cleanup owner/repo#N` prompt itself exempt the PR (a session-scoped record, no
  label), with no label-add policing. Rejected implicitly. The label is what makes the exemption visible on GitHub and
  durable across sessions, which justifies the extra R6 surface. No change proposed.

### 3d. Edge cases & UX
- **Issues labelled `cleanup`.** FR-010 / R6 refuse `gh issue edit N --add-label cleanup` and
  `gh api repos/O/R/issues/N/labels`. That endpoint and that command also label *issues*, and the label's own
  description ("Code cleanup, dead code removal, or refactor…") is an issue-triage label. The plan resolves the PR
  with `fetch` (`gh pr view N`), which fails for an issue number. Whether that refuses or allows is unspecified. If it
  refuses, ordinary issue triage is blocked; if it allows, behaviour depends on an unplanned error path. (E1)
- **Label semantics.** A human (or the user, on GitHub) who tags a refactor PR `cleanup` for triage, as the label
  description invites, silently exempts it from every alq-review gate, with no prompt. (P2)
- **Label absent in a repo.** `cleanup` exists only in `claude-plugins-internal`. Elsewhere, `gh pr edit --add-label
  cleanup` fails *after* the hook spent the grant (R5: spent when the command passes the hook). The user must grant
  again after creating the label. Same as `override-merge` today; minor. (E5)

### 3e. Success measurement
- SC-001 should name its repo scope. In `analitiq-core` / `claude-code-plugins` the org gate still holds the PR
  (FR-005), so SC-001 is met only where no org pr-gate runs. (P3)

## Engineering Lens

### 4a. Architecture
- One decider, readers differing only in transport (R1), mirrors `version_only_release`/`released`. Good.
- The label check in `pre_merge_gate` (every mode) and not in `gate.py` (log-mode-lifted) is the right call for P2.
- Exit `5` for the poller: the only consumers found are the skill and the tests. `pr_dossier.sh` and
  `block-adhoc-pr-polling.sh` in `cto/.claude` reference the poller by name but do not branch on its exit code. No
  change needed.

### 4b. Failure modes
- **Commit path latency** (R4): `gate.on_bash` would call `pr_target` then `pr_labels` before
  `claimgate.on_commit` (`gate.py:361`) on *every* commit, in every repo with alq-review on, labelled or not. Each call
  can take up to `_answer`'s 20 s; with gh hanging (offline, auth prompt) that is 40 s of a 60 s hook budget before
  claim-check starts. One call, `gh pr list --head <branch> --state open --json number,labels`, gives both answers
  and halves the worst case. (E2)
- Unread label → gated, refusal names why (FR-007, P4). Correct.

### 4c. Security / trust
- **Exemption outlives its purpose** (Clarification 3, FR-001). After one grant the agent can push any code to the
  PR and merge it with no internal review, no Codex, no claim/shim check. The user granted "cleanup", not "anything
  pushed later". It is a user decision, so not a violation. But P2 asks for one approver and one action, and the grant
  becomes an unbounded release. (Q1)
- Non-gh label routes (curl with the token, a script) stay open; stated in R6 and on a par with the attestation's
  limit. Acceptable as stated.
- `gh api graphql` forms other than `addLabelsToLabelable`/`labelIds` (e.g. `updatePullRequest` with `labelIds` is
  covered; `addLabelsToLabelable` via a `--input` file or `-F query=@file` is not text-visible). R6 says text-matched
  unparseable commands are refused, but a query loaded from a file is invisible. Same class as the curl limit. List it
  under "Not closed". (E3)

### 4d. Performance
- See E2. Ready/merge/poller: one call each, fine.

### 4e. Testing
- Each scenario maps to a test (quickstart). Missing cases: issue-number label add (E1), grant spent then gh fails
  (E5), and the commit path with gh hanging (E2). (E4)

### 4f. Operational readiness
- Rollback = remove the label or revert the plugin version. No state migration, and the `.cleanup` record is
  session-scoped. Fine.

### 4g. Dependencies
- None new.

## Cross-Lens Insights

- **X1 (FR-012 commit exemption).** It costs gh calls on every commit everywhere (E2), widens what the label exempts
  (Q1), and does not fire in the flow that motivated the feature (3b). Dropping it would shrink scope, risk and
  latency together. It was a clarified user decision, so this is a question, not a change.
