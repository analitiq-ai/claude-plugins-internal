## Executive Summary

The problem is observed, reproduced and traced to one line of the poller; the fix reads the artifact that
actually says whether Codex finished, puts the decision in a pure module with its own tests, and keeps the
poller's exit codes and the inbox drop unchanged. Spec, research, data model and contract agree with each
other almost everywhere, and the constitution check is honest. Two things block task generation as written:
the spec is silent on the one existing flow the new rule reverses (Codex out of credits with the org gate's
`WAIVED` run, pinned today by `test_the_waiver_is_printed` at exit 0, exit 4 under the spec, with a BLOCKED
line that contradicts itself), and FR-010 and plan R6 disagree on the exit code of a `declined` round with
open findings. Both are spec edits. The remaining items are the brittleness of the acknowledgement list
(a Codex wording change stalls every consuming repo until the plugin is patched, even when the card already
says Codex finished), a Python-version trap in the date parsing, and the enumeration of unreadable reasons,
which the plan extends past FR-007.

### Failure Mode Analysis
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E2 | 💡 | R4 parses the Status cell's `datetime` with `datetime.fromisoformat`. A trailing `Z` is accepted only from Python 3.11. CI pins 3.13, but the poller runs on whatever `python3` the user's machine has, and no minimum is declared anywhere in the plugin. On 3.10 every card is `unreadable` ("datetime … is not ISO-8601"), exit 1 on every poll. | GitHub's `datetime` attribute is always `%Y-%m-%dT%H:%M:%SZ` (the format `ledger.py` already prints). Parse with `strptime` on that exact format in R4; anything else is unreadable. No version floor needed. |
| E5 | 🤔 | A second `@codex review` while a review runs is not probed (Assumptions). Under R5, the Running row's `status_at` is before the new `since`, so the state is `not_started`; when the row flips Completed with `status_at > since`, it is `answered` for a review that began before the trigger. For an unchanged head that is the right answer; for a head pushed between the two triggers it is `superseded`, also right. | Either probe it once on a live PR, or write the reasoning above into Edge Cases so the test exists and the behaviour is chosen rather than incidental. |
