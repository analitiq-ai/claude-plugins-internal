# Critique Report: spec.md is read-only on a story branch (#104)

**Date**: 2026-10-13
**Feature**: [spec.md](../spec.md)
**Plan**: [plan.md](../plan.md)
**Verdict**: ⚠️ PROCEED WITH UPDATES

---

## Executive Summary

The direction is sound and simplifies the gate: a write-time rule replaces an after-the-fact hold, and the ledger stops
keeping a copy of the spec's identity. US1, US2 and US4 are well specified, pure, and testable. Most of the risk is in US3
(`rebase <ref>`): the spec says it rebases on the default branch while the plan rebases on the PR's base, which breaks for
the stacked story PRs this plan itself ships (R1). The resolver's admitted `git add` can stage a spec.md, against FR-009,
and the bare `--force-with-lease` is weaker than the spec's "nothing is forced". There is also a shipping-order gap: the
rescope route is broken between US1 merging and US5 releasing. All of these can be fixed in the plan without rethinking it.

| ID | Severity | Finding | Suggestion |

| E1 | 🎯 | The spec (US3, FR-009) rebases on the **default branch**. The plan (R9) rebases on `github.pr_target`, which is the PR's `baseRefName` (`github.py:53`). For a stacked story PR (R1 stacks US2 on US1 and US3 on US2), the base is the parent story branch. | E2 | 💡 | The plan's P1 row says the resolver dispatch is "as every workflow launch is". But a hook reply that asks the session to call `Agent(...)` is a step that depends on an agent obeying. ### Failure Mode Analysis
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E3 | 🎯 | `rebase_admits` admits the resolver's `git add -- <paths>` when every path is unmerged, with **no spec.md exclusion** (R10, data-model "What the conflict resolver may do", interfaces row 4). An unmerged spec.md can be staged as is, or after `git checkout --theirs spec.md` (no `--`, which the writes table doesn't cover), and `rebase --continue` then commits it. The commit backstop never sees that commit. This breaks FR-009's "never a spec.md". | Exclude any `spec_md_folder(path)` from admitted `add`. Have `_rebase` / `after_bash` treat an unmerged spec.md as unresolvable: abort and raise it to the user. Add a test. |
| E4 | 💡 | `rebase <ref>` runs fetch, rebase and push inside a UserPromptSubmit hook with a 120 s timeout. If the hook is killed mid-rebase, a rebase is in progress with **no** `rebase` record. The next `rebase <ref>` then reaches step 7 and `git rebase` fails with "already in progress". This state is not covered by the step table. | Add a step: a rebase in progress with no record means reply naming it, and tell the user to run `git rebase --abort` in `<root>`. Set `GIT_SSH_COMMAND='ssh -o BatchMode=yes'` alongside `GIT_TERMINAL_PROMPT=0` so an SSH passphrase prompt can't hang the hook until it times out. |
| E5 | 💡 | A bare `git push --force-with-lease origin <branch>` checks against the local `origin/<branch>` tracking ref. Any background fetch of that ref (IDE, another session) quietly defeats the lease. The spec promises "nothing is forced" when the remote moved. | Pin the lease: `--force-with-lease=<branch>:<sha>`, where `<sha>` is the branch tip before the rebase (`rebase.from`, or the locked round's `head_sha`, whichever the remote last had). Test a remote that moved after a fetch. |
