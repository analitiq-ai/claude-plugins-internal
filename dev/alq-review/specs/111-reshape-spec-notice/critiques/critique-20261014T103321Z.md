# Critique: 111-reshape-spec-notice

**Date**: 2026-10-14 | **Artifacts**: spec.md, plan.md, research.md, data-model.md, contracts/, quickstart.md (no tasks.md yet)
**Template**: `.specify/templates/critique-template.md` does not exist; structure follows the skill's outline.
**Code read at**: `25bd2e2` (`gate.py`, `policy.py`, `ledger.py`, `github.py`, `hooks.json`, `assess-round.js`, `tests/workflow_harness.mjs`). Nothing was run.

## Executive Summary

The design is small, well-placed and mostly verified against the code: the ruling is recorded once
(`on_structured_output` refuses a second assessor output in every mode), the claim/call/record split keeps
`gh` out of the `BEGIN IMMEDIATE` transaction, and the unlock and refusal texts reuse existing renderers.
One spec-level contradiction blocks tasks: FR-013 promises the comment carries no local path, while the plan
posts assessor free text verbatim (plan Open question 1). Two plan defects should be fixed before tasks: the
hook-time budget ignores the second ledger open, and quickstart scenario 2 assumes the harness runs a nested
workflow, which it does not.

**Verdict: ⚠️ PROCEED WITH UPDATES**

## Product Lens

### 3a. Problem validation
- Clear harm, traced to code (`_reshape_brief` has one caller, `_unlock`). Scope is tight. No finding.

### 3b. User value
- **P1 🤔** `escalate_to` is a bot account (`Analitiq-Bot-Wonka`). Assigning the issue to a bot signals
  "escalated" but notifies no human owner; only issue subscribers see the comment. Confirm the bot is watched
  (or acts) — otherwise US2's "reaches the spec's owner" is not met.

### 3c. Alternatives
- Considered and rejected in clarifications (linked issue, outbox, retry). No finding.

### 3d. Edge cases
- **P2 💡** After `unlock`, a stored notice failure is no longer shown anywhere (lock refusal is gone, unlock
  reply is one-shot). A user who unlocks without reading the reply loses the only signal. Acceptable by
  FR-010 ("fixed by hand"), but state it in the spec's Edge Cases so it is a decision, not an omission.

### 3e. Success measurement
- SC-001…005 are all test-checkable. No outcome metric (e.g. reshapes picked up from GitHub vs. from the
  session). Fine for an internal plugin; no finding.

## Engineering Lens

### 4a. Architecture
- `reshape.py` pure, `gate.py` I/O, `policy._holds` reads `current_round`, matching
  `policy.reshape_spec_ruling` — same round on both surfaces. Sound.

### 4b. Failure modes
- **E1 💡** Time budget. Plan says "two `gh` calls at most, each capped at 20 s" fit the 60 s PostToolUse
  timeout. The hook also runs `ledger.ingest_inbox` first, the ruling's `open_ledger`, and then a *second*
  `open_ledger` for `record_notice`; `sqlite3.connect(..., timeout=60)` can wait up to 60 s on a busy ledger.
  Worst case: the hook is killed after GitHub answered but before the outcome is stored, and the user sees
  "GitHub's answer was not recorded" for a notice that succeeded. P4 keeps it honest, but the plan's budget
  claim is wrong. Suggest: name the full budget in the plan, and either skip the edit call when the deadline
  leaves < 20 s plus margin (stored as its own failure) or accept and document the window.
- **E2 💡** `record_notice` raises `LedgerError` if an outcome is already set. In PostToolUse that crash
  "fails open" with a `systemMessage` (`gate.main`). Fine, but the plan should say so, since it is the
  path a duplicate delivery racing a first delivery would take.

### 4c. Security & privacy
- **E3 🎯 (constitution II; spec contradiction)** FR-013 says the comment carries "no local path, ledger
  content or session detail, since the issue may be in a public repository". The plan posts `user_decision`,
  `rationale` and each `mechanism` verbatim — assessor free text that can name absolute paths, ledger refs or
  internal detail — and leaves it as Open question 1 while marking Principle II PASS. Either FR-013 is
  narrowed to "what the gate adds" (and the residual risk accepted explicitly), or the plan adds a control.
  This must be decided in the spec before tasks. Options, smallest first:
  (a) brief the assessor that these three fields are published (prose — weak under P1);
  (b) post the full summary only when `github.repo_visibility` is private, and a pointer-only comment
  (folder, PR, round) in a public repo — `repo_visibility` already exists;
  (c) accept the risk and reword FR-013.
  Recommendation: (b) — code decides, reuses an existing read, and keeps the public case within ADR-0008.

### 4d. Performance
- Not relevant beyond E1.

### 4e. Testing
- **E4 💡** Quickstart scenario 2 says "harness runs the nested assess-round". `workflow_harness.mjs` does
  not: a nested `workflow(name, …)` returns the canned `answers[name]` and logs the call. Split it into
  (2a) review-round's recorded `calls` show `spec_folder` forwarded to `alq-review:assess-round`, and (2b)
  assess-round run directly with `spec_folder` in args returns it. Otherwise the forwarding in
  `review-round.js` is untested.
- **E5 💡** Add a scenario for E1's window: outcome left `null` (hook killed between claim and record)
  renders "GitHub's answer was not recorded" in both the refusal and unlock reply. The data model defines
  it; quickstart has no row for it.

### 4f. Operational readiness
- Label created by hand before ship (quickstart). No rollback concern: removing the notice code leaves only
  an inert `notice` key. No finding.

### 4g. Dependencies
- **E6 🤔** Assumption "the `gh` token can comment, label and assign in every repo the plugin runs in" is
  listed as not investigated. In particular `--add-assignee` fails unless `Analitiq-Bot-Wonka` has access to
  that repo. Confirm the bot is a collaborator in each repo the plugin runs in, or accept the failure path
  as the expected outcome there.

## Cross-Lens Insights

- **X1 🎯** E3 is both a product and a trust question: the comment's value is the summary, and the
  summary is exactly the part that can leak. Option (b) keeps full value where it is safe and still tells
  public-repo owners a reshape is waiting.
