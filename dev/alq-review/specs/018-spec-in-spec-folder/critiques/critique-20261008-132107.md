## Executive Summary

The direction is settled by the user and the design follows it well: one module owns the pointer's form, the gate resolves branch → issue → comment → folder in one function, refusals name a next step, and every mechanism cites a research decision. Three items must be fixed before `/speckit-tasks`. (1) The plan itself records a Principle VI violation (the pin test is replaced in the same PR as the skills it grades) and leaves it "open for the user". (2) `has_committed_specify` is specified over `git ls-files` (the index) while `spec.md` is read from HEAD, so "committed" means two things. (3) Nothing says the spec folder is committed and pushed before the location comment is posted, yet the comment's meaning is "the spec is finished, work may start" and tackle checks out the `branch:` it names. The rest are recommendations: how hard the new refusal lands on existing issue-numbered branches, a spec that the change under review can edit, and `alq-shape` overwriting the pointer.

Claims about code below were checked by reading `github.py`, `briefs.py`, the `design-doc` workflow and the constitution. Nothing was executed.
