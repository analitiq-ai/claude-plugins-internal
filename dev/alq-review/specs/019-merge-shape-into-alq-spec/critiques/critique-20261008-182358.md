## Executive Summary

The direction is settled and the design follows it: the three checks become workflow steps, the form of each document is defined once (`premise_report.py`, the preset template, `speclocation.py`), the location comment keeps one owner, and the Spec Kit behaviour the shape rests on is put to a red test first (R10). Three items must be fixed before `/speckit-tasks`. (1) The skill's "spec already exists" pre-check, built on `speclocation.py show`, cannot tell "a spec exists" from "the comment refuses", so two edge cases the spec promises cannot work as written. (2) The root cause check accepts `Not a defect report.` for an issue the premise report calls a defect, which is the exact escape FR-004 closes at the premise step. (3) FR-020 assigns FR-021 to neither pull request. The rest are recommendations.

What was checked: `workflow.yml` of `design-doc`, `speclocation.py` and its callers (`gate.py`, `briefs.py`) were read. Nothing was executed; the Spec Kit gate and `if` behaviour is still only read (R10 covers it).

## Product Lens Findings 🎯

### Problem Validation
No finding. Two planning skills that disagree is a real, stated defect, and the user chose the merge.

### User Value Assessment
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| P1 | 🎯 | The spec says a re-run on an issue marked "no spec needed" or "not worth doing" runs the `premise` step (edge cases), and that a premise that fails on a re-run for an issue that was specced before stops the run. R7 says the skill first runs `speclocation.py show <n>`, and "a folder found means the spec exists" so it stops. But `show` goes through `located`, which after FR-018 raises for the not-worth-doing form, and which exits 1 for a missing or malformed comment too. The skill cannot tell those exits apart, so a not-worth-doing issue is refused instead of re-asked. And for a specced issue the stop comes before the workflow, so "the premise fails on a re-run" can never be reached. | Give the pre-check one outcome per form: a `status` command (or `show` exit codes) that says located / no spec / not worth doing / none, and say in the spec which of the two re-run edge cases survives. Drop the one that cannot happen. |
| P2 | 💡 | On "not worth doing" the only record is the one-line `reason:`. The six answers and their sources live in a run folder that is not committed (data-model: "Not committed"). A later reader hitting the tackle refusal gets one line and cannot see which question failed. | Make the `reason:` convention name the failed question (`reason: harm cannot happen on main (predicted)`), and say so in the contract. Nothing else needs to be kept. |

### Alternative Approaches
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| P3 | 💡 | `premise_report.py check` is a form check: a `Source: code: foo.py` is not looked at. Nothing in the spec says so, while FR-021 says it for the root cause ("checks that the section is there and labelled, not that the trace is right"). A reader of FR-011 would take "a run that skips one fails" as a guarantee about truth. | Add the same sentence to FR-011: the script grades the form and that a source is named, not that the answer is right; the user's pick is the judgement. |

### Edge Cases & UX
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| P4 | 💡 | `check` demands all six answers with sources even for "not worth doing". An issue whose harm is "none" has no honest `reachable` answer starting `observed` or `predicted`, and the user is made to fabricate one to stop the run. | For the two stop picks, require only the questions up to the one that failed plus `Reason:`; or allow `reachable` to start `n/a`. Decide and write it in the contract. |
| P5 | 🤔 | The report's `Pick:` must equal the gate's choice. The plan does not say whether `steps.premise.output.choice` is the canonical option string or the text the user typed (R1 says the gate matches case-insensitively). If it is the typed text, `Pick: not worth doing` against `Not Worth Doing` fails the run for a spelling. | Settle in R10 (assert the stored `choice` for a mixed-case resume) and compare case-insensitively if it is raw. |

## Engineering Lens Findings 🔧

### Architecture Soundness
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 🎯 | `rootcause.py check <spec folder>` accepts `Not a defect report.` whenever the section has it. The premise report holds `Reports wrong behaviour: yes`; nothing joins the two. `premise_report.py check` refuses "no spec needed" for a defect, but at `specify` the model can write `Not a defect report.` for the same issue and the run passes, skipping the trace. The size of the fix is then decided with no root cause. | Pass the report to the check: `rootcause.py check <spec folder> <report>` fails when the report says yes and the section is `Not a defect report.`. One more argument, same module. |
| E2 | 💡 | `root-cause` runs right after `specify`, before `grill`, and the user corrects the trace in grill (FR-021). After grill nothing re-grades the section, so the correction can delete the `Observed:` line and the run carries on to `plan`. | Run the same step again after `no-open-markers` (a second step calling the same script, not a second implementation). |
| E3 | 🎯 | FR-020 lists what each pull request carries: PR 1 "FR-001 to FR-012, FR-014 to FR-016, FR-018, FR-019", PR 2 "FR-013, FR-017". FR-021 (the root cause step) is in neither, and FR-020 is not a requirement of either. A task list built from FR-020 drops the root cause gate. | Add FR-021 to PR 1's list. |

### Failure Mode Analysis
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E4 | 💡 | `record-outcome` posts through `gh`; if it fails after `premise` is approved, the run fails with the gate already passed and the user's pick not written. Re-driving the run re-asks the pause, since the gate has no stored verdict. | Say in R1 whether `resume` on the failed run re-uses the verdict (the verdict is passed as an input on resume, so it should) and pin it with one test in R10. |
| E5 | 💡 | Two location comments can already refuse the run (`_comment` raises on more than one). `record` posts after a pause that may be long; another session can add a second comment in between. | Covered by the existing error with its next step; no change, but put it in the tests list so the refusal at `record` is shown, not assumed. |

### Security & Privacy Review
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E6 | 💡 | R-notes say the pick reaches the shell "only as one of three fixed option strings the gate has matched". That holds only if the gate rejects a verdict that matches none of its options. The existing workflow comment states that template text is spliced into shell source before the shell can validate it. | Make R10 assert that a resume with a verdict outside the three options fails at the gate, and have the shell steps read the pick from the environment (as `$SPEC_DIR` does) rather than from spliced template text. |
