## Executive Summary

The spec and plan are unusually well settled: every classification turns on a named adrkit rule, every scenario has a
named test, and the design follows the plugin's existing boundary/pure-rule split. Research says nothing was run; this
critique read adrkit 0.20.0's shipped JavaScript (`@adrkit/core` and `@adrkit/cli` under `~/.node22`) and the plugin
on `main` to check the contract claims, and they hold: `lint --json` is `{checked, findings}` with no records, `check`
carries lint findings only for changed records, the CLI exposes no repo qualifier, symlinks and non-files both come
back `unreadable`, exit codes are 0/1 for reports and 2 for an unreachable corpus, and the marker window is 8192 bytes.

Two items must be addressed before tasks. First, refusal row 5 names `npm install` as the fix for a governing id that
has two files, but two files with one id is a corpus defect adrkit itself reports (`unique-id`, severity `error`), so
the named step cannot succeed: that breaks ADR-0009 point 3 and P1, which the plan marks Pass. Second, the check has no
release of its own: FR-009/FR-010 refuse in both modes, there is no per-check setting like `claim_checks` and
`shim_checks`, and `alq-review off` refuses the round workflows too, so a machine where adrkit chronically fails cannot
run any internal round. That is the exact condition ADR-0011 names under "Revisit if". The second item touches a
settled clarification (FR-018), so it is also a question for the user.

Product-wise the mechanism delivers the stated harm reduction, but the org-corpus value is narrower than the issue
implies: a repo-qualified matcher is never enforced anywhere, including the repo it names. adrkit core already
implements repo-aware evaluation (`member`); only the CLI lacks the flag. That is the cheapest route to the full value
and should be named in the spec.
