# 28 random commits, claude-code-plugins, last 60 days

## Methodology

**Preparation**
1. Population: 638 non-merge commits in the 60 days before 2026-10-01 (merge commits excluded) from `analitiq-ai/claude-code-plugins`.
2. Sample: 30 commits via `random.sample`, seed 20261001. The 2 whose only change was `.gitignore` were dropped, leaving 28.
3. Files: all files changed per commit (`git show -U0 -M`), then trimmed for testing: max 12 files per extension per commit, sampled toward ~30 py / 30 json / 20 yaml / 20 md, at least one file kept per commit.
4. Hunks: every hunk of each kept file, one table row per hunk. Hunk = `-old,count +new,count` line range from `git show -U0` (old file lines removed/changed, new file lines added/changed). 326 rows.

**Step 1: categorise Action (ADD / REMOVE / CHANGE), deterministic, from git**
Derived from the hunk header counts (a missing count means 1):

| Header | Action |
|---|---|---|---|---|---|
| old count = 0 (`-a,0 +b,n`) | ADD |
| new count = 0 (`-a,n +b,0`) | REMOVE |
| both counts > 0 | CHANGE |

CHANGE means git saw lines both removed and added; it does not imply the meaning changed (a whitespace-only rewrite is CHANGE).

**Step 2: categorise Kind (CODE / PROSE / MIXED), by subagents**
- CODE: pure code or machine structure: Python, TypeScript, shell, and structural config/schema content (YAML/JSON keys, values, structure, identifiers, paths, versions).
- PROSE: pure human-language text: documentation, Markdown text, description/message/help strings, docstrings, comments.
- MIXED: the hunk changes both code and prose at once.
- Judged from hunk content, not file extension.
- Run: a workflow of 12 Sonnet subagents at medium effort, one per batch of ~3-20 files (~22 KB of diff each). Each read its batch's hunk text (hunks over 60 lines truncated to the first 60) and returned one structured label per hunk. All 326 hunks labeled; no hunks missing or duplicated.


**Step 3: categorise claims in PROSE hunks (K1-K8), by subagents**
- Scope: only the 123 hunks labeled PROSE in Step 2; other rows are left blank.
- Task given to the agents: for each hunk, determine if there is a claim in the wording of the hunk; if so, categorise it into one of:
  K1 what our own code, contracts, validator or CI does; K2 how a vendor tool, cloud platform, language or standard behaves; K3 a list, a count, or an "every / the only / complete" claim; K4 a task tick or a PASS/FAIL status mark; K5 a recorded observation, such as a date, run ID, commit, count or approval; K6 a command or code block and what it does; K7 a citation of a file, field, symbol, rule or requirement; K8 planned behaviour, meaning what a proposal or design says the system will do once it's built.
- Run: a workflow of 8 Sonnet subagents at medium effort, 11-16 hunks each, one structured entry per hunk (quoted claims, each with one category).
- Column "Claim categories": the distinct categories found in the hunk (a hunk can carry several claims, so several categories), or `none` when the agent found no claim. Quotes are not stored in this file.
- Not reviewed by hand.

**Step 4: assess correctness of K1 claims (test subset of 30 hunks), by subagents**
- Scope: hunks whose Step 3 categories include K1 (what our own code, contracts, validator or CI does) and whose K1 claim quote appears in the hunk's added lines (77 hunks qualified). 30 sampled at random (`random.seed(30301)`), one K1 claim per hunk (chosen at random if several); the claim text is the quote extracted in Step 3, unedited. Other rows are blank in the three columns.
- Source of truth: a read-only export (`git archive`) of the repo at the row's commit; the file and line given to the agent are the doc location of the claim (line computed from the hunk header).
- Run: 30 Sonnet subagents at medium effort, one claim each, searching and reading the checkout with Read/Grep/Glob/shell. Agents were told to split the claim into assertions, read the implementing code, look for failing cases, then give a verdict (prompt supplied by the user; `${READONLY}` was filled with an instruction to read and search only, never modify files).
- Verdicts: CORRECT = every assertion confirmed by code read and no failing case; WRONG = at least one assertion false or has a failing case; UNSURE = code settling an assertion could not be found or read.
- Columns: "K1 claim checked", "Claim verdict", "Verdict basis" (agent's own summary). Per-assertion evidence (file:line) is not stored in this file.
- Not reviewed by hand. Several claims are sentence fragments from Step 3, so an agent may have judged a wider or narrower claim than a human would.
