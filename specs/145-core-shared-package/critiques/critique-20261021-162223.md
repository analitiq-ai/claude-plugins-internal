## Executive Summary

The problem is real and well evidenced: the orchestrator imports no plugin code, so without `core/` it
cannot read identity, state or findings. Every mechanism cites an ADR or a research decision. Three gaps
stand between this plan and a working deployment. First, deleting the newest state comment is not
detected, although reviewer ADR-0011 says a deleted snapshot that releases a hold means the design is
wrong. Second, the rescope-hold command has no named credential, and US5 is ranked last although US2's
read trusts only the session App. Third, the Finding and Snapshot contracts are born without a way to
record a pushback on a finding that has no thread, which root ADR-0003 d7 requires; the plan defers it to
a contract change later. Two smaller items are a CI module that can pass a repo whose required checks it
cannot see, and a lock `probe` that can make a real take fail.

Nothing here was run. Every finding comes from reading the spec, the plan, the research, the contracts
and the cited ADRs.

## Engineering Lens Findings 🔬

### Architecture Soundness
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 💡 | Version skew between pins: reviewer, planner, builder and the orchestrator each pin core on their own, and users update plugins one at a time. A `Snapshot` posted by a newer core (`v: 2`, or a new field) fails `extra="forbid"` in an older reader and reads as `invalid`. Then that older reviewer's `release_rebuild` posts an older-format snapshot that drops the newer data. ADR-0011 Consequences names the cost ("a snapshot format change is a core release every component pins") but does not define what a reader does with an unknown version. | Add a held cause, `unknown_version`, distinct from `invalid`. Have `post` and `release_rebuild` refuse when the newest snapshot's `v` is higher than the reader's, naming the core version needed. Add a row to data-model's State read transitions. |

### Failure Mode Analysis
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E2 | 🎯 | Deleting the newest state comment is not detected. FR-015 and FR-016 detect an edit (`lastEditedAt`) but not a deletion. If the comment that opened a hold is deleted, the one before it becomes the newest unedited comment, and the hold is gone. Reviewer ADR-0011 rejects exactly this (Option E: "deleting … the newest comment would drop the hold it placed") and names "an edited or deleted snapshot releases a hold" as its "how we would know this was wrong". Any writer can delete: humans with write access, and the session App, which has `issues: write`. This breaks P2: a hold is released by an action no decision record names. | Have every snapshot carry `prev`, the `databaseId` of the comment it replaces, and a monotonic `seq`. A reader that has seen a comment remembers the newest `(id, seq)` it saw: the ledger cache of ADR-0011 d5 for reviewer, and the orchestrator's own record. When that id is gone, or the newest `seq` is lower, the read is held as `deleted`. A first-time reader cannot detect a deletion that happened before it ever read. If that residual gap is not acceptable, the plan must say the layer cannot meet ADR-0011 and propose amending it (Principle III). Add FR-016 text, an acceptance scenario, and a Q2 row. |
| E3 | 💡 | `lock.probe` takes `LOCK_EX \| LOCK_NB` and then releases it (R15). While it holds the lock, a real `take` is refused, and the refusal names the holder from JSON left by an earlier holder. A `take` that reads the file between another taker's `flock` and its write gets an empty file and cannot name the holder. | Probe without taking the lock: `fcntl` `F_OFD_GETLK` through `struct flock`, which reports a conflicting lock without acquiring one. Write the holder JSON to a sibling file with an atomic rename before releasing the pipe. A refused take that finds no holder record names "holder unknown", not an exception. |
| E4 | 💡 | The first install builds a venv and runs `pip install git+https://…` of a private repo inside the hook's existing 60 s budget (plan Performance Goals). On a host with no cached git credential, git prompts on the terminal and hangs until the hook is killed. The failure is then reported as a timeout, not as its cause, which works against FR-003's "report the installer's error". | Run pip with `GIT_TERMINAL_PROMPT=0` and `--no-input`. Give the `SessionStart` entry its own explicit timeout sized for a cold install, and add a Q1 row for "no git credential → exit 2 naming git's auth error". |

The spec does not say how the token then reaches `gh` for the session's writes; each Bash call is a fresh shell, so `GH_TOKEN` does not persist.
