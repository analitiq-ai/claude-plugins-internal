## Engineering Lens Findings 🔬

### Architecture Soundness

- **E1 🎯 The rescope hold keeps a stale spec PR.** contracts/state-comment.md (Write rules) and R16 say
  `placeRescopeHold` "posts nothing when the row is OPEN". FR-020 and reviewer ADR-0013 d5 say it posts nothing
  only when the row already records that spec PR, and "a new spec PR places the hold again". The main rescope
  path breaks: a RESCOPE verdict places the row with `spec_pr` null; planner opens spec PR #301 while the row is
  OPEN, so the plan posts nothing and the row still records null; after the release, reviewer's hook sees #301
  open, the row does not record it, and the hold is placed again.
  *Fix*: posts nothing when the row records that spec PR, open or released; otherwise the row is OPEN, `since`
  from `now()`, recording the spec PR.

- **E2 🎯 The tamper release can post nothing.** contracts/state-comment.md says `releaseOnClaim` posts "nothing
  when nothing is released". FR-019 says the release path posts the snapshot rebuilt from the newest unedited
  valid one. With a released tamper cause and no open hold, nothing is posted, the edited comment stays the
  state comment, the cause stands, and every later `writeState` is refused.
  *Fix*: `releaseOnClaim` posts when it releases a hold or a tamper cause; R16 says the same in place of "when
  anything changed".

- **E3 💡 Core's answers over a module lack two inputs.** contracts/core-api.md: `status(module, repo, pr, head,
  {timeoutSeconds, since})` needs `now()` for SILENT, and `findings(module, repo, pr, head)` needs the four App
  logins to drop App threads (R19). Neither is passed.
  *Fix*: a loaded module carries the `deps` and `shared` it was loaded with (`loadValidators(shared, dir, deps)`);
  say so in core-api.md and R18.
