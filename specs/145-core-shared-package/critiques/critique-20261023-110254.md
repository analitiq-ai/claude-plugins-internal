## Engineering Lens Findings 🔬

### Architecture Soundness
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E9 | 🎯 | `isDone(reader, repo, s)` can't find a merged story's PR. R13 finds it by the story's branch, and orchestrator ADR-0009 d6 deletes head branches on merge. The issue is closed by the PR's `Closes #s` at the orchestrator App's merge (d4), so the `User` closer rule doesn't apply. Result: `isDone` returns false for every orchestrator-merged story, breaking FR-011 and US1 AS9. | Take candidate PRs from the issue's timeline: `ClosedEvent.closer`, `CONNECTED_EVENT` and `CROSS_REFERENCED_EVENT` sources that are PullRequests. Accept one only when it is merged, same-repo, and its `headRefName` parses to `{story: s}`. The branch stays the link (root ADR-0005 d3); the timeline only finds candidates. Add a fixture with the branch deleted and a Bot closer. |
| E3 | 🎯 | The DeepSource `api` source reads `deepsource-token` through `readKey(name, plugin)`, but `enabledModules(settings, reader)` and the module methods take no plugin (core-api.md). The gate read cannot be made. | `enabledModules(settings, reader, plugin)`. Update core-api.md and quickstart. |

### Failure Mode Analysis
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 🎯 | The missing-dependency guard fails open. An uncaught `MissingDependency` makes `node` exit 1, and Claude Code treats exit 1 as a non-blocking error: "The action goes ahead … If your hook is meant to enforce a policy, use `exit 2`" (hooks docs). A Node too old to run `.ts` fails the same way, as does a hook timeout. This breaks FR-003 and root ADR-0004 d2 (fail closed). | In carrying-core.md: every hook that runs core is declared with `"onFailure": "block"` (Claude Code ≥ 2.1.295, per the docs), and it catches `MissingDependency` and exits 2 naming the package. The US1 fixture hook shows both. |
| E2 | 🎯 | The no-answer signal misses GitHub's rate-limit answers. Per GitHub's docs, a GraphQL primary limit answers `200` with `errors`, and a REST secondary limit answers 403 or 429 with `retry-after`, not necessarily `x-ratelimit-remaining: 0`. R12 classifies by status only. A GraphQL read can return empty data, and a REST secondary limit becomes `GitHubRefused`, against FR-024. | In R12: a GraphQL answer with non-empty `errors` never returns `data`. `RATE_LIMITED`, or any 403/429 with `retry-after`, is `GitHubUnanswered`; any other GraphQL error is `GitHubRefused`. Add fixtures in US1. |
| E4 | 🎯 | `findings` returns `[]` where a check could not run. R22 makes findings "one per FAIL check", so a required check in `error` gives `[]` (AS5). The DeepSource `github` source is the same: its status covers FAIL/PASS/SILENT only. FR-024 says never an empty list. | R20 and R22: `findings` is COULD_NOT_RUN when any check it reads maps to COULD_NOT_RUN. R20's status uses R22's order: FAIL, then COULD_NOT_RUN, then PASS, else PENDING. |
| E10 | 🎯 | The state read cannot order a deletion against the newest comment. R15 fetches no comment `createdAt`, yet decides `deleted` by "a deletion newer than it", and `databaseId` cannot be compared with an event time. This breaks FR-016 and US2 AS2. It also leaves no way to tell whether a release repost is newer than the deletion. | Add `createdAt` to the fetched comment fields. Compare `deletion.createdAt > stateComment.createdAt`. |
| E6 | 💡 | A version bump can pass on a stale base. Two PRs each change `core/src` and each bump a carrier from v to v+1; `pull_request` checks don't re-run, and there is no up-to-date rule (orchestrator ADR-0009 d6). The second merges cleanly and ships a core change under an installed version. | Also run the carriers check on `push` to main against `HEAD~1`, failing loudly and naming the carrier. |

### Security & Privacy
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E5 | 💡 | GraphQL `author.login` carries no `[bot]` suffix (the poller strips it, `poll-pr-review.sh` 131, 211–215). R21 compares thread starters with `[bot]`-form vendor and session logins. Codex's threads would land in `untrusted`, and the session App exclusion would miss. | R21 normalises as R15 does: a `Bot` author's login plus `[bot]`. Add a fixture. |
| E11 | 💡 | Token permission names are not GitHub's API keys. The API names org projects `organization_projects`, and key-files.md writes `projects`. GitHub may also add `metadata: read` to a token answer unrequested (not verified), and R24's equality check would then refuse every mint. | Hold the permission sets as API keys, with the §3 drift test mapping prose to keys. Refuse an answer that lacks or lowers a requested permission, or grants any other permission than `metadata: read`. Confirm on the first real mint in US5. |

### Testing Strategy
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E7 | 💡 | `keys.ts` lands in US3, but the key-gate acceptance scenarios sit in US5 AS4. Following the split, they would be written after the code (Principle IV). | R26: `keys.ts` and its gate tests land in US3. |
| E8 | 💡 | The fixture plugin's `core` link (`../../../src`) is not matched by the `*/plugin/core` carrier glob, so its pins can drift. Quickstart step 1 copies it where the link points outside the marketplace, and step 5 needs a carrier the repo lacks. | A US1 test checks the fixture's pins against core's. The quickstart recreates the link as `../../core/src` and adds a throwaway carrier for step 5. |
| E12 | 💡 | Spec-facts values (`kind`, `observed`) are written inline in SpecFacts, outside the value-string test, so `requirement`'s `no_spec` check can be a bare literal. | Export them as named enums from `contracts/spec-facts.ts`, spelt as planner ADR-0008 fixes them, and extend the value-string test to every enum core defines. |
