# Critique: The orchestrator plugin carries core

**Spec**: [spec.md](../spec.md) | **Plan**: [plan.md](../plan.md) | **Date**: 2026-10-30 | **Tasks**: not generated

`.specify/templates/critique-template.md` and the extension's `check-prerequisites.sh` do not exist in this

## Executive Summary

The spec and plan are tight, well-sourced and consistent with the ADRs and with core on `main`: every core
function the plan cites as existing exists (`needsMint`, `writeGhToken`, `readKey`, `laneOf`, `specIssue`,
`specPr`, `isDone`, `readState`/`startable`, `releaseOnClaim`, `attests`, `runGit`, `status`/`StatusWindow`,
`appLogins`, `gitHubTree`), and the carrier fixture already uses `"onFailure": "block"`. The crash-between-lane-
write-and-record analysis (R9) holds against `startable`'s definition (`core/src/state.ts:321`).

One must-address item: every hook takes the repository from the checkout's `origin`, which the model can
rewrite from a sandboxed Bash call. The rest are recommendations that tighten Story 1's contract and Story 2's
delivery shape.

## Engineering Lens Findings

### 4a. Architecture Soundness
- **E3 💡** orchestrator ADR-0001 d3 says "We will drive the loop from four hooks" (SessionStart, PreToolUse,
  UserPromptSubmit, Stop). R16 adds SubagentStart/SubagentStop. They record and drive nothing, so there is
  arguably no conflict, but the plan does not say so. Suggest: one sentence in R16 saying they feed Stop's
  decision and drive no step, or an ADR amendment in its own PR.

### 4b. Failure Mode Analysis
- **E4 🤔** FR-021 justifies the in-hook wait with "Claude Code's limit of 8 Stop refusals in a row". Nothing in
  the repo sources or tests that limit. If it is real, it also caps Story 2's step loop: every builder step is a
  Stop refusal, so a story needing more consecutive steps would be force-ended with its Stop hook having run but
  the session not marked ended, and counted toward `k_deaths`. Suggest: cite the source, or run it on the agent
  machine (R20's recorded-input task can do both), then either bound consecutive steps below the limit or delete
  the sentence.

### 4c. Security & Privacy Review
- **E1 🎯** *Repository from a model-writable source.* Plan P8 and contracts/gh-config-folder.md take the
  repository from the checkout's `origin`. The managed settings deny `.git/config` to the Edit tool only
  (`SECURITY.md:130`); the sandbox's `denyWrite` (`SECURITY.md:122`) does not list it, and the checkout is
  writable to sandboxed commands. So `git remote set-url origin <other>` in one Bash call changes the repository:
  - the next PreToolUse sees `needsMint` (another repo) and mints a session token for it, breaking US1 #4's
    "for the checkout's repository alone";
  - UserPromptSubmit claims, and Story 2's Stop pushes, opens, attests and merges with the orchestrator App,
    against whichever installed repository `origin` names.
  The checkout outlives the session, so a rewrite in one session carries into the next session's SessionStart.
  Suggest: (a) add the checkout's `.git/config` (and `config.worktree`) to sandbox `denyWrite` in PR M, beside
  the existing Edit deny; and (b) after the claim, every hook takes the repository from the session's issue
  record (FR-014 already stores `repo`), never again from `origin`, refusing when the two differ.
- **E2 💡** R13's open test, "can a sandboxed command read a hook child's environment through `/proc`", covers
  less than the exposure. The Stop hook holds the orchestrator token for up to 3600 s while the model's
  background Bash tasks keep running, and the model cannot stop them because `TaskStop` is denied
  (`SECURITY.md:158`). Suggest: the C7 test runs a `run_in_background` reader started before the turn ends, and
  reads both `/proc/<pid>/environ` of the git child and the Stop hook's own process.

### 4d. Performance & Scalability
- **E5 💡** R5 says "a hook" reads `app_id`/`session_app_id` from HEAD, mints the orchestrator token, then reads
  the settings from GitHub. Applied to PreToolUse, that is an orchestrator mint and a tree read on every Bash
  call, which contradicts the plan's goal that PreToolUse "adds no GitHub call while the stored token has ≥ 10
  min left". Suggest: R5/R7 state that PreToolUse reads only the gh folder and the repository, and reads
  settings only when `needsMint` holds.

## Cross-Lens Insights

- **X1 💡** *Story 2 is several stories.* It covers FR-016 to FR-024, seven ADRs and core PRs C6–C12, and
  runs live only after #209. As one issue it is one story PR, the size the review loop's file-edit tripwire is
  meant to stop. Suggest splitting it along the ADRs into independently testable stories, each with its own
  core PRs:
  (2a) push, draft PR, agent identity, builder skill edit (C7, C12 passed-commit record);
  (2b) attest, exempt, ready (C10);
  (2c) modules, replies, In review, merge, Stop's wait (C8, C9, C11);
  (2d) bound counts (C6).
  This adds no scope: it is the same FRs in smaller PRs, and each lands as soon as its core PRs do.
- **X2 💡** *SessionStart's failure post cannot report the failures it exists for.* FR-008 posts on
  `status_issue` with the orchestrator App. That needs the orchestrator key, managed settings in effect and a
  GitHub settings read. Those are the failures US1 #6 names, so the post fails too and SessionStart exits 0 with
  nothing reported. The spec's own edge case already covers this: the next UserPromptSubmit mints again and
  refuses loudly. Suggest: drop FR-008 and `status_issue` (Story 1 then reads two keys), or have SessionStart
  also write the cause to stderr so the session shows it.
