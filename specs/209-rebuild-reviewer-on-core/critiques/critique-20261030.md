## Executive Summary

Spec and plan are tightly argued, cite their decisions, and keep core as the single contract owner. Fail-closed
behaviour is consistent. Four must-address items: (1) core's state writes are read-then-POST with no
serialisation, so two concurrent reviewer hook runs can drop a hold or round — an unapproved release (P2);
(2) the commit-check pass record fixes one issue/branch per session file, contradicting the spec's own "two
claims in one session" edge case and US2-1's second `<s>-us<k>` branch; (3) cutover deletes the ledger's open
holds and counts with no approved entity named (P2: nothing may release or lower a count but its approver);
(4) the after-commit base is not checked for ancestry, so an amend/rebase past the newest pass grades a
meaningless range. The rest are recommendations.

## Engineering Lens Findings 🔬

### Architecture Soundness
| ID | Severity | Finding | Suggestion |

| E1 | 🎯 | Pass record contract (`commit-pass-record.md`) holds one `repository/issue/branch` per session file and `recordCommitPasses` "refuses a … issue/branch differing from the file's". The spec's edge case allows two claims in one session, and US2-1 allows `42-us2-logout` beside `42-us1-login`. Either case makes every later pass throw → permanent could-not-run. ### Failure Mode Analysis
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E4 | 🎯 | Core writes are read-modify-POST (`untamperedSnapshot` → `post`, `core/src/state.ts:464-485`) with no compare-and-swap; newest comment wins. Claude Code runs hooks for parallel tool calls/subagents concurrently, so e.g. `placeHold(claim-7)` and a `writeState` round, or two `placeHold`s, built from the same reading lose one write. A lost hold row is a release by no approved entity (P2); a lost round silently stalls attestation. `checkTransition` only catches a stale snapshot passed in by the caller, not a concurrent post. | Serialise every reviewer state/gates write in a session with an exclusive lock file in the session folder (held across read→post), and add a test with two concurrent writers against the recorder. The same lock covers R9's concurrent claim steps. Hosts on one machine/one session, so a local lock suffices. |
| E5 | 🎯 | R10 grades `base..head`, base = newest pass. After an amend/rebase/reset, base may not be an ancestor of head: `base..head` then includes or omits unrelated commits, and the orchestrator's push of the newest pass may be a non-fast-forward of what it would push next. Same for a GitHub head that is not an ancestor of local head. | Add to R10 and the state machine: if base is not an ancestor of head, re-base from GitHub's branch head; if that is not an ancestor either, refuse (history rewrite of pushed commits) naming the next step. Add a quickstart scenario. |
| E6 | 💡 | A claim hold needs two writes (gates `wrong_at` append, then `placeHold`) on two comments, non-atomic. | Specify order: post the gates evidence first, then re-derive and place the hold on every deciding run whose count ≥ threshold and hold not OPEN, so a crash between them is repaired on the next run. Pin with a test. |
| E7 | 💡 | First check on an empty bare copy fetches the GitHub branch head "with the session token" — a full-history fetch on a large repo can exceed the 60 s hook timeout, and on timeout the run is could-not-run forever. | Read the GitHub head sha via the API, then fetch that object from the local clone (content-addressed, so trust holds); fall back to a GitHub fetch only when the clone lacks it, outside the hook path if needed. |
