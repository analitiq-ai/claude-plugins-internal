# Research: Planner carries core

Each decision below settles one mechanism of [plan.md](plan.md). "Not run" marks a behaviour read from docs or
code but not executed; the story that relies on it starts with a red test that runs it.

## R1: Story order and where core's additions land

- **Decision**: Five PRs, one per story, in the order US1 → US2 → (US3, US5 in either order) → US4. Each core
  capability lands in the PR of the story that first uses it (FR-016): US2 the gh token folder, the remote
  parser and the push credential; US3 the spec-facts writer and the premise vocabulary; US4 the branch-name
  builder, the spec-PR lookup, the spec-folder answer, the lane read and the task-block label grammar. Each PR
  that changes `core/src` bumps planner's `plugin.json` version, as every planner PR must for its change to reach
  an install.
- **Rationale**: US1 is the only story with no core code run inside planner, and every later story needs it.
  US4's writes need US2's token. One PR per story is org ADR-0003; a capability landed apart from its first user
  would be an API with no caller.
- **Existing tools**: Spec Kit's story phases and the repo's sub-issue chain (planner ADR-0010) fit as they
  are; #174's records (PR #175) are reused, and it adds no core code this plan could reuse.

## R2: Planner as a carrier

- **Decision**: `planner/plugin/core` is a symlink to `../../core/src`. `planner/plugin/package.json` is
  `{"name": "planner", "private": true, "type": "module", "dependencies": <core's three pins>}` with a v3
  `package-lock.json` generated by `npm install --package-lock-only` in that folder. No devDependencies: an
  install fetches the lockfile's packages into the plugin (SECURITY.md §7, 2.1.312). `plugin.json`'s
  `version` stays pinned and goes 0.2.0 → 0.3.0 in US1.
- **Rationale**: This is the shape `check-carriers.ts` grades and the fixture models; nothing in the check needs
  to change.
- **Existing tools**: `core/tests/fixtures/carrier-plugin` (copied as the model); `core/scripts/check-carriers.ts`
  (finds any `*/plugin/core`, so planner is picked up with no edit to it).

## R3: One guarded entry for every planner TypeScript entry point

- **Decision**: `planner/plugin/lib/guarded.ts` statically imports only `../core/guard.ts`, runs
  `requireDependencies()`, and on `MissingDependency` writes `core dependency <name> is not installed in <root>`
  to stderr and exits 2. Every TypeScript script imports it first, statically, then loads everything else with
  `await import(...)`.
- **Rationale**: Root ADR-0009 d4 and FR-003. A static import of any other module would be evaluated, and fail on
  the missing package, before the guard ran. One module, so no two scripts can word or code the refusal
  differently.
- **Existing tools**: `core/src/guard.ts` (used as is); the fixture's `hooks/identity.ts` shows the pattern,
  which this lifts into one module instead of repeating it per entry.

## R4: Planner's TypeScript tests and CI

- **Decision**: `planner/package.json` (component root, never installed) is a private package with
  devDependencies `typescript` 7.0.2 and `@types/node` 22.20.5 (core's pins) and the script
  `"test": "tsc -p . && node --test 'tests/**/*.test.ts'"`; `planner/tsconfig.json` mirrors core's and includes
  `plugin` and `tests`. In `.github/workflows/tests.yml` the suite job runs, for suite `<c>/tests`:
  `npm ci` in `core`, in `<c>/plugin` when it holds a `package-lock.json`, and in `<c>` when it holds a
  `package.json`, then `npm test` in `<c>`; and `python -m unittest -v` when the suite holds a `test_*.py`. The
  `core/tests` special case goes; core falls out of the same rule.
- **Rationale**: FR-004 asks every carrier's TypeScript tests to run. A rule keyed on what a component holds,
  not its name, covers the next carrier with no edit (P8 in spirit). In this repo `planner/plugin/core` resolves
  to `core/src`, and Node resolves a module's imports from its real path, so core's own modules need core's
  `node_modules`; planner's own modules need the plugin's.
- **Existing tools**: core's `package.json`/`tsconfig.json` (copied); `node:test` and `tsc` as core uses them;
  the existing matrix in `tests.yml` (kept, its two `if:` steps replaced by the two conditions above).

## R5: Planner's scripts mint when they need the token

- **Decision**: Planner declares no hook: no `hooks/hooks.json`, no `hooks/token.ts`, no session record.
  `plannerToken(repo, appId, now, mint)` in `planner/plugin/lib/github.ts` reads the stored token from
  `ghFolder(repo)` (R6) and, when `needsMint` reports it missing, another repository's, or under 10 minutes left,
  mints with `mint`, core's `mintToken("planner", appId, "planner-app.pem", "planner", repo)` in production, and
  stores it with `writeGhToken`; it returns the token. `plannerGitHub` connects with it, and `StaleToken` goes.
  Every script reads settings (R7) and the repository (R8), then calls one of them before its first GitHub call;
  `mint` is injected, so tests use a fake. `KeyReadRefused`, `MintError`, `GitHubRefused`, `GitHubUnanswered`,
  `SettingsError`, `RemoteRefused` and `NoOrigin` exit 2 with core's message (root ADR-0004 d1); a missing key's
  read error, which core lets through naming its path, is re-thrown.
- **Rationale**: The admin's ruling of 2026-10-29 (spec Clarifications) and root ADR-0007 d4 and ADR-0008 d2 as
  amended with it: planner's token acts only in planner's own GitHub calls, and the session's other commands keep
  the admin's gh login. 10 minutes exceeds any script's run: each makes its calls within a minute of starting.
- **Existing tools**: `mintToken` in `core/src/tokens.ts`; `needsMint`, `readGhToken`, `writeGhToken` in
  `core/src/gh-config.ts` (all used as is). Rejected: the session hook this spec first chose, on `SessionStart`
  and on `PreToolUse` matching `Bash`, with a session record and the session's environment (R9): it swapped the
  admin's gh credentials out of every command in the session, and refused every Bash call when a mint failed. Its
  run on 2026-10-28 (T015, Claude Code 2.1.312, `claude -p`) stays as the record of what Claude Code does: a
  `SessionStart` hook that exits 2, or exits 1 with `"onFailure": "block"`, does not stop the session; a
  `PreToolUse` hook gets no `CLAUDE_ENV_FILE`.

## R6: The token in planner's gh config folder

- **Decision**: New core module `core/src/gh-config.ts`. `writeGhToken(folder, token, login)` writes
  `hosts.yml` (`github.com: {oauth_token, user: <login>, git_protocol: https}`) and `codeworks-token.json`
  (`{repo, expires_at}`) through a temp file and a rename each, folder mode 0700, files 0600.
  `readGhToken(folder)` returns `{value, repo, expires_at}` or null when absent, refusing a half-written folder.
  `needsMint(stored, repo, now)` is pure: true when null, another repo, or under `REFRESH_MARGIN_MS` (10 min)
  left. Planner's folder is `~/.local/state/codeworks/planner/<owner>/<name>/gh`, one per repository, from one
  function, `ghFolder(repo)` in `planner/plugin/lib/settings.ts`, which the scripts call. A script mints through
  `plannerToken` (R5) when `needsMint` is true.
- **Rationale**: FR-005/FR-006 and the clarifications: planner's gh and git read only this folder. A
  folder per repository keeps two planner sessions in two repositories from overwriting each other's one-repo
  token. The orchestrator's hook needs the same write and refresh (root ADR-0007 d2), so it is core's.
- **Existing tools**: gh's own `hosts.yml` (used, so `gh` and `gh auth git-credential` read the token with no
  wrapper); `gh auth login --with-token` (rejected: by gh's docs it may store the token in the system keyring,
  outside the folder; not run). Not run: that current gh reads
  `oauth_token` from `hosts.yml` under `GH_CONFIG_DIR`; US2's contract test runs `gh auth token` on a written
  folder.

## R7: Planner's settings

- **Decision**: `plannerToken`'s callers read settings with `readSettings(gitTree(checkout, "HEAD"))` and validates
  `section("planner")` with `PlannerSettings = z.strictObject({ app_id: z.number().int().positive() })` in
  `planner/plugin/lib/settings.ts`. A `SettingsError` or a refused section exits 2 with
  `codeworks.toml [planner]: <why>`. US2 adds this repo's `codeworks.toml` with the values the spec's
  Assumptions list.
- **Rationale**: Root ADR-0002 d2–d4: one file at the ref the component works on, its own section validated by
  the component, unknown keys refused, no environment override. The App's login comes from
  `[shared] planner_app_login`, which core already validates.
- **Existing tools**: `readSettings`, `gitTree` in core (used as is).

## R8: The checkout's repository and its https URL

- **Decision**: New core function `repositoryOfRemote(url)` in `core/src/github.ts` takes an origin URL
  (`https://github.com/o/n(.git)`, `git@github.com:o/n(.git)`, `ssh://git@github.com/o/n(.git)`) and returns
  `{owner, name}`, refusing any other host or shape; `httpsUrl(repo)` returns
  `https://github.com/<owner>/<name>.git`. The scripts read origin with
  `runGit(checkout, ["remote", "get-url", "origin"])`.
- **Rationale**: US2 #6: the push goes to the https URL whatever origin is, so no SSH key carries it. `plannerToken`
  needs the repository to mint for, the landing script to push to. One parser for both.
- **Existing tools**: `ownerAndName` in core (takes `owner/name` only, reused for validation after the parse);
  `new_issue.py` and the workflow pass origin's URL to `gh --repo` (gh parses it; not reachable from TypeScript).

## R9: Planner's gh for a script that is not TypeScript

- **Decision**: `planner/plugin/scripts/gh.ts <gh args…>`, guarded (R3), reads settings (R7) and origin's
  repository (R8), gets the token through `plannerToken` (R5), then runs `gh` with those arguments, stdin, stdout
  and stderr passed through, `GH_CONFIG_DIR` set to `ghFolder(repo)` and core's `GH_TOKEN_VARIABLES` removed from
  its environment, and exits with gh's code. `new_issue.py` runs its `gh` calls through it. Planner writes nothing
  to the session's environment.
- **Rationale**: US6 #3: the issue `new_issue.py` creates is a write, so it is the planner App's (SC-005).
  FR-017 keeps `new_issue.py` in Python, since it calls no core. gh reads a token from those variables before its
  config folder, so one left set would let the admin's token act. The skill's `gh issue view` is a read and runs
  with the admin's login (spec Assumptions).
- **Existing tools**: core's `GH_TOKEN_VARIABLES` (used as is). Rejected: the session's environment through
  `CLAUDE_ENV_FILE` (R5's rejected hook); porting `new_issue.py` to TypeScript (a rewrite for one call site).

## R10: The push carries the token from gh

- **Decision**: `runGit` gains an optional `env` argument merged after its own. New core
  `pushWithGhCredential(checkout, ghConfigDir, repo, refspec)` runs
  `runGit(checkout, ["-c", "credential.helper=!gh auth git-credential", "push", "--porcelain", "--end-of-options", httpsUrl(repo), refspec], [], env)`
  with `GH_CONFIG_DIR=ghConfigDir`, `GIT_TERMINAL_PROMPT=0`, and core's four `GH_TOKEN_VARIABLES` removed.
  `runGit`'s own `credential.helper=` comes first, so the helper list is exactly gh's.
- **Rationale**: The clarification rules git reads the token from gh. runGit's arguments follow its
  `NO_CONFIGURED_CODE`, so a later `-c credential.helper` adds one helper to an emptied list; the global and
  system config stay unread. The env is passed, not inherited, so the push is right whatever the caller's
  environment holds.
- **Existing tools**: `runGit` (extended, not copied); `gh auth git-credential` (gh's documented helper). Not
  run: the helper's answer for a `hosts.yml` written by R6; US2's test runs `git credential fill` through the
  same config with the real gh and checks `username`/`password`.

## R11: Spec facts written through core

- **Decision**: Core adds `writeSpecFacts(text, facts)` to `core/src/contracts/spec-facts.ts`: it parses
  `facts` with `SpecFacts`, then either sets the `codeworks` key in an existing leading front matter (other keys
  kept, through `yaml`'s `parseDocument`) or prepends `---\ncodeworks: …\n---\n`. Planner adds
  `planner/plugin/scripts/spec_facts.ts write <folder> [<premise report>]` with a pure `specFactsOf(wrong, opening)`:
  kind `no_spec` for a no-spec spec.md, else `defect`/`feature` from the report's `Reports wrong behaviour`;
  observed `none` for `Not a defect report.` or no-spec, `hypothesis` for an opening that starts with the
  template's hypothesis sentence, `anchored` for any other `Observed:` opening. The workflow runs it after
  `write-no-spec` (no report: kind `no_spec`) and after `premise-answers-after-grill`; a rescope does not run it
  (its landing is #178's).
- **Rationale**: FR-008, planner ADR-0008 d1, P7: readers get keys, never a heading. A writer and reader in one
  module round-trip by construction. Running it after the last grading step is what US3 #4 needs: grill's
  rewrite is graded, then the block is rewritten. Per ADR-0008 d1 the settled-design preset's
  `templates/spec-template.md` opens with the block, its values ones `SpecFacts` refuses, so a spec the writer
  never filled fails core's reader; the writer sets the key there. A no-spec spec.md does not come from the
  template (`no_spec.py` writes it), so the writer prepends the block to it. `no_spec.is_no_spec` then reads the
  first line after a leading front matter block, so a no-spec folder still routes a rescope to `premise`
  (`spec_folder.starts_at`); `spec_facts.ts`'s no-report check applies the same rule.
- **Existing tools**: `readSpecFacts`, `SpecFacts` (core, reused); `yaml` (a core pin); `rootcause.py` and
  `premise_report.py` (they grade the same lines and stay Python, FR-017; they do not call core).

## R12: One vocabulary for the premise report and the root cause opening

- **Decision**: Core adds `core/src/contracts/premise.ts` holding, once, the labels and values both languages
  read: the three picks, `Reports wrong behaviour` with `yes`/`no`, `Observed:`, `Not a defect report.` and the
  hypothesis sentence. `core/scripts/write-schemas.ts` also writes them to `core/src/generated/premise.json`,
  checked by the drift test; `premise_report.py` and `rootcause.py` load that file through
  `planner/plugin/core/generated/premise.json` and drop their own literals; `spec_facts.ts` imports the module.
- **Rationale**: FR-016 and root ADR-0010 d3: a value is spelled once. Two parsers now read these lines, so the
  words must have one source. The file sits under `core/src` because only that reaches an installed plugin.
- **Existing tools**: `valueSet` and `write-schemas.ts` with its drift test (extended); `core/schemas/`
  (rejected as the target: not shipped).

## R13: Run preconditions: lane and open issue

- **Decision**: Core adds a `Lane` value set (Backlog, Ready, In progress, In review, Blocked, Done; orchestrator
  ADR-0002) to `values.ts` and `laneOf(reader, repo, issue, board)` to a new `core/src/board.ts`, returning the
  card's lane on `[shared] board`, null for no card, and refusing a status outside the set. Planner adds
  `planner/plugin/scripts/preflight.ts <issue>` as the workflow's first step: it stops naming the card to move
  (outside Backlog/Blocked), the card to add (null), or the closed issue; a GitHub that does not answer stops it as
  could-not-verify (P4).
- **Rationale**: FR-012, planner ADR-0005 d3, root ADR-0006 d1. The orchestrator, reviewer and builder read
  lanes too, so the read and the set are core's. A workflow step makes it code, not prose (P1).
- **Existing tools**: `state.ts` reads lane changes from a timeline for history (not the current lane);
  `GitHubClient.graphql` (used).

## R14: The spec PR on `<p>-spec`

- **Decision**: Core adds `specBranch(p)` to `identity.ts` (tested as `parseBranch`'s inverse) and
  `specPr(reader, repo, p)` with a pure `pickSpecPr(prs)`: the newest same-repository PR whose head is
  `<p>-spec`, as `{number, state: open | closed | merged}`, or null. Core also adds
  `specFolderAnswer(names, p)` returning `{one} | {none} | {several}`; `pickSpecFolder` is rebuilt on it.
- **Rationale**: FR-011, planner ADR-0010 d3. `pickSpecPr` mirrors `pickStoryPr`. The landing needs to tell
  "no folder on the default branch" (a new spec) from "several" (stop naming them), which `pickSpecFolder`
  throws alike.
- **Existing tools**: `parseBranch`, `pickStoryPr`/`storyPr`, `pickSpecFolder` (core; reused and extended).

## R15: Story issues and their chain

- **Decision**: The landing script reads the stories as the `[US<k>]` tags in tasks.md (Spec Kit's grammar).
  One story: the story is `<p>`, nothing is created. Several: it lists `<p>`'s sub-issues in order; sub-issue
  `i` is `US<i+1>`; it creates the missing ones in order (`POST /repos/{o}/{r}/issues`, then
  `POST …/issues/<p>/sub_issues` with the new issue's `id`, then
  `POST …/issues/<new>/dependencies/blocked_by` with the previous story issue's `id`). More sub-issues than
  stories stops the run naming the extra ones. On a re-run, tasks.md's task-block labels already name each
  story's issue; a sub-issue at position `i` other than the issue `US<i+1>`'s label names stops the run naming
  both, since a story issue's number never changes (planner ADR-0010 d1). Titles are `US<k>: <story title>` from
  tasks.md's phase heading.
- **Rationale**: FR-009, planner ADR-0010 d1. Sub-issue order is a GitHub field, so a re-run finds what it
  made without reading text (P7) and never creates a story twice (US4 #7).
- **Existing tools**: `GitHubClient.rest` (core). Not run: the sub-issue and `blocked_by` REST endpoints; US4
  runs them against the fake GitHub, and its quickstart step runs them once against GitHub.

## R16: Task-block labels

- **Decision**: Core adds the label grammar, a line `Story issue: #<n>` directly under a phase heading, with
  `taskBlockLabel(n)` and `readTaskBlockLabels(text)` in `core/src/contracts/tasks.ts`. Planner's pure
  `labelTasks(text, issues)` writes one per phase: a phase holding `[US<k>]` tasks gets story k's issue; phases
  before the first story phase the first story's, after the last the last story's; an existing label line is
  replaced.
- **Rationale**: FR-010, planner ADR-0008 d2; reviewer ADR-0010 reads the label to grade ticks, so the grammar
  has two readers and one home. Phases are told apart by their task tags, never by heading words.
- **Existing tools**: Spec Kit's stock tasks template (kept, ADR-0008 d2). None fit for the label itself.
  Looked at: core, reviewer's scripts, the presets.

## R17: The landing

- **Decision**: `planner/plugin/scripts/land.ts <issue> <spec dir> <kind>` replaces SKILL step 8's commit and
  push. It first fetches the default branch and `<p>-spec`. Reads first, in order: kind `rescope` stops naming #178; the spec folder answer at `HEAD` and on the
  default branch (several, or a folder already on the default branch, stops); the paths changed since
  `merge-base(HEAD, origin/<default>)` must lie in the spec folder or a `docs/adr/` folder; `specPr`: closed stops naming the branch, merged stops naming #178; with
  an open PR, `origin/<p>-spec` must be an ancestor of `HEAD`. Then writes: story issues (R15), labels (R16),
  a commit as the planner App (`user.name` = `planner_app_login`, email from `GET /users/<login>`'s id), the push
  (R10) to `refs/heads/<p>-spec`, and, with no open PR, a draft PR to the default branch. It prints the spec
  folder, the branch and the PR URL.
- **Rationale**: FR-006, FR-009–FR-011, FR-014; every stop comes before the first write (US4 #5, #8). A commit
  as the planner App keeps every planner write its App's (SC-005). A script decides, the skill only calls it (P1).
- **Existing tools**: `runGit`, `gitTree`, `gitHub` (core). Rejected: the skill committing with the admin's
  git (its identity, not the App's, and tasks.md is relabelled after the issues exist).

## R18: Not worth doing closes nothing

- **Decision**: The `close-not-worth-doing` step becomes `name-close`, which prints
  `Close #<issue> as not planned: <reason>` from `premise_report.py reason` and calls no `gh`. SKILL step 3 and
  `plugin.json`'s description say the admin closes it.
- **Rationale**: FR-015, planner ADR-0006 d1–d2.
- **Existing tools**: `premise_report.py reason` (used as is).
